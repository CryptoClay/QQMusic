# Очередь, метаданные и проверка нескольких пользователей

## Управление загрузками

На странице **Загрузки** есть пауза очереди и три приоритета: обычный, повышенный, срочный. Изменения относятся только к текущему аккаунту и работают на всех его устройствах. Пауза хранится в SQLite и переживает перезапуск.

Пауза прекращает захват новых заданий скачивания и раскрытия альбомов. Уже взятые воркерами файлы завершаются: прерывания загрузки на произвольном байте нет. Сопоставление переноса и служебное сканирование Navidrome продолжаются. Новые загрузки можно добавить в приостановленную очередь; обычные квоты действуют. После продолжения учитываются приоритет и заданная задержка повторного запуска. Срочный файл не прерывает уже работающий воркер.

В строке ожидающего повторения показываются число попыток и время следующего запуска. Автоповтор ограничен существующим `jobs.max_attempts`, задержка растёт от 5 секунд до 10 минут. Для скачивания повторяются распознанные временные ошибки: таймаут, разрыв сетевого соединения, 408/425/429 и HTTP 5xx. Запрет доступа, вход/cookies/CAPTCHA, отсутствие файла, неправильные данные, нехватка квоты и неизвестная программная ошибка автоматически не повторяются. Другие источники по-прежнему пробуются в рамках текущей попытки. Кнопка ручного повтора остаётся доступной после устранения причины.

Ручные повторы сериализуются в SQLite: два одновременных нажатия не создают два новых задания. Старые ожидающие задания терминальной загрузки выводятся из работы. Проверки владельца и квоты сохраняются, включая пакетный повтор.

## Порядок в тегах

**Настройки → Проверка библиотеки → Порядок в тегах**. Раздел доступен администратору:

- поиск треков по исполнителю, альбому и названию, до 100 на странице;
- подсчёт отсутствующих номеров, годов и обложек;
- варианты написания имени по Unicode, регистру, пробелам и е/ё, с ручным выбором канонического имени;
- пакетная правка исполнителя, жанра, номера диска;
- последовательная нумерация выбранных треков в порядке списка, начиная с указанного числа;
- переход к полной дате релиза и обложке альбома.

Перед каждой правкой браузер показывает список «было → станет» для каждого трека. До нажатия **Применить изменения** файлы и база не меняются. Выбор на странице очищается при смене поиска/страницы. За один запрос сервер принимает до 500 треков. Издания, clean/live/remix и состав исполнителей автоматически не склеиваются. Выбор жанра с пустым полем явно очищает его, что видно в предпросмотре.

На странице альбома можно указать `YYYY-MM-DD`. Год синхронизируется с датой; изменение года с несовместимой полной датой очищает эту дату с отображением в предпросмотре. При других правках полная дата сохраняется в тегах. Новые каталожные альбомы сохраняют дату из источника; прежние даты не угадываются.

Выбранная обложка подготавливается в браузере до 768 px, затем показывается в предпросмотре. Сервер проверяет изображение и подписывает операцию вместе со снимком библиотеки. После сторонних изменений старый предпросмотр получает 409. Аудиофайлы, UUID и варианты треков сохраняются; файлы ретегируются. Размеры файлов обновляются для корректного учёта пользовательского объёма. Для ошибок пакетной операции предусмотрено восстановление исходных файлов вместе с откатом SQLite. После подтверждения операция завершает запись или откат даже при отключении браузера; процесс сервера при этом должен продолжать работать. Прежние прямые API редактирования оставлены для совместимости клиентов.

## Воспроизводимая проверка нагрузки

`scripts/benchmark_music.py` создаёт отдельный временный каталог и базу, собственные аккаунты, сеансы и короткие WAV-файлы. Рабочая база и музыка не открываются. Проверяются атомарный захват заданий, сохраняемая пауза, ограничение параллелизма, импорт файлов и изоляция очередей/личных заметок. Для каждого пользователя задаётся `parallel=1`.

Из корня проекта, без подключения рабочих томов и внешней сети:

```powershell
docker build -f hub/Dockerfile -t qqmusic-hub:check .
docker run --rm --network none --tmpfs /tmp -e PYTHONPATH=/app -v "${PWD}/scripts:/checks:ro" --entrypoint python qqmusic-hub:check /checks/benchmark_music.py --users 10 --tracks 20 --workers 10 --requests 40
```

Последняя строка — JSON-отчёт. Ненулевой код завершения означает обнаруженную ошибку. `--requests` задаёт число циклов на пользователя: в каждом читаются очередь и личные заметки; `measured_queue_reads` — количество замеренных чтений очереди, `total_api_requests` включает заметки, их первоначальную запись и продолжение очереди.

Локальный прогон 13.11.2026: 10 пользователей, 200 импортов, 10 воркеров, 400 замеренных чтений очереди и 811 API-запросов всего. Все 200 заданий завершились; двойных захватов, превышений настроенного параллелизма и утечек между аккаунтами не обнаружено. Время — 18,36 с; медиана чтения очереди — 152 мс, p95 — 223 мс. При меньшем прогоне (6 пользователей, 48 файлов) — около 16 мс и 50 мс соответственно. Это измерения конкретного Docker-хоста, а не обещание производительности. SQLite последовательно выполняет записи, поэтому при росте числа одновременных импортов задержки увеличиваются. Скорость внешних источников, FFmpeg-транскодирования и реальных сетевых аудиопотоков этот сценарий не измеряет.
